# Viva — Questions and Answers

All answers below are grounded in the actual implementation of Venture AI. No result is invented.

---

## General

**1. What is Venture AI?**

A full-stack AI-powered platform that connects startups with investors. It combines a React frontend, a Spring Boot backend, a MySQL database, and a FastAPI AI microservice hosting three deep-learning models: a startup potential/risk predictor, a two-tower recommendation model, and a BERT pitch-deck analyzer.

**2. What problem does it solve?**

Three problems: (a) discovery friction between founders and investors, (b) shallow early-stage evaluation, (c) lack of structured feedback on pitch decks. Venture AI addresses all three through structured profiles, AI-driven scoring, and recommendation ranking.

**3. Why did you choose this project?**

It combines two domains I care about: applied deep learning and startup finance. It also exercises every layer of modern full-stack engineering — secure auth, relational persistence, a Python ML service, and containerized deployment.

**4. Who are the target users?**

- **Startup founders** creating profiles, running predictions, analyzing pitch decks
- **Investors** maintaining a preference profile and receiving AI-ranked recommendations
- **Admins** overseeing platform analytics and model metadata

## AI

**5. Why use deep learning?**

The prediction task involves non-linear interactions across 36 features — team size, growth rate, runway, funding, industry interactions — that linear models underserve. Deep learning captures interactions directly from data. The recommendation task is inherently embedding-based, which deep learning handles naturally.

**6. How does the startup prediction model work?**

A multi-output Keras MLP. Input is 36 features. Outputs are (a) a scalar potential score (0–100) trained with MSE, and (b) a 3-class risk category (LOW/MEDIUM/HIGH) trained with weighted sparse categorical cross-entropy. A custom training loop applies per-sample class weights to counteract class imbalance. Training stopped at 92 epochs with `EarlyStopping(patience=15)`.

**7. What is the Two-Tower model?**

An architecture with two independent encoder networks: one for startups, one for investors. Each encodes its input into a fixed-size embedding. The similarity between embeddings — cosine — is the compatibility signal. This is a standard pattern for recommendation systems because it scales well: embeddings can be precomputed and candidates ranked by vector similarity.

**8. Why use embeddings?**

Embeddings map heterogeneous inputs (numeric + categorical, from different feature spaces) into a shared low-dimensional space where similarity is meaningful. Without embeddings, comparing an investor profile to a startup profile is a matching problem. With embeddings, it becomes a vector dot product.

**9. How is compatibility calculated?**

`50 * (cosine_similarity(l2_norm(startup_emb), l2_norm(investor_emb)) + 1)` → score in [0, 100]. Both towers L2-normalize their outputs before the similarity step. The factor of 50 and offset of 1 remap the cosine range [-1, 1] to [0, 100].

**10. Why use BERT?**

Pitch-deck text is short, dense, and section-structure heavy. Classical methods (bag of words, TF-IDF) lose word order and contextual meaning. BERT's bidirectional attention captures context and works well on small fine-tuning datasets — exactly the setup here.

**11. What does the pitch analyzer do?**

It chunks input text, runs BERT over each chunk to classify it into one of 8 sections (Problem, Solution, Market, Product, Business Model, Traction, Competition, Team), aggregates per-section confidence, computes an overall completeness score, and emits a list of information gaps (missing or low-confidence sections).

**12. What is synthetic data?**

Data generated programmatically to have the statistical structure of real data but no real-world identity. Our startup, investor, and pitch-deck datasets are all generated by scripts in `ai-service/training/`. This lets us demonstrate the full ML pipeline without requiring licensed or private data.

**13. Why can't synthetic results be considered real investment performance?**

Because the training targets are themselves synthetic — we computed potential score as a deterministic weighted function of the features. The model learns to approximate that function. Excellent fit on synthetic data means the model correctly reversed the generator — not that it can predict real startup success. Any claim about real-world performance would require validation on real data.

## Backend

**14. Why Spring Boot?**

It provides an opinionated, production-grade foundation with first-class Spring Security, Spring Data JPA, and validation. It's the industry standard for JVM REST APIs and integrates cleanly with JJWT for stateless authentication.

**15. Why FastAPI?**

Its async I/O and Pydantic-based schema validation pair well with model-serving workloads. It loads TensorFlow and Transformers natively, and the automatic OpenAPI docs are useful for testing. It also keeps the Python ML stack fully isolated from the Java application.

**16. Why separate the AI service?**

Two reasons: (a) language ecosystem — TensorFlow and HuggingFace are Python-only; running them inside the JVM is impractical. (b) Independent deployment — the AI service can scale, restart, or be swapped without affecting the backend.

**17. How does JWT authentication work?**

On login, the backend verifies the password against a BCrypt hash and issues a signed JWT (HS256). The token carries `sub=email`, plus `userId` and `role` claims. Subsequent requests attach `Authorization: Bearer <token>`. A `JwtAuthenticationFilter` validates the signature, loads the user from the database, checks `enabled`, and populates `SecurityContextHolder`. No server-side session is stored.

**18. How are roles handled?**

Two layers: (a) `SecurityConfig` restricts `/api/admin/**` to `hasRole('ADMIN')`; (b) individual controllers use `@PreAuthorize("hasRole('STARTUP')")` and `@PreAuthorize("hasRole('INVESTOR')")`. The service layer additionally verifies the user's role before state-changing operations.

## Database

**19. Why MySQL?**

Relational, transactional, mature, and widely supported. Startup and investor data is highly structured; the ownership relationship (User → Startup, User → Investor) is naturally relational.

**20. What are the main entities?**

Three JPA entities: `User` (id, name, email, password hash, role, enabled, timestamps), `Startup` (company details, financials, traction, stage, industry, business model, owner FK), `Investor` (name, type, preferences, investment range, risk, owner FK).

**21. How are users and startups related?**

One-to-(0..1). A user with role `STARTUP` may own at most one startup profile. The `Startup` table has a `user_id` FK with a unique constraint. Ownership enforcement happens at the repository level via `findByIdAndUserId`.

## Frontend

**22. Why React?**

Component model, declarative UI, mature ecosystem, hooks-based state management. It fits well with a role-based multi-dashboard application.

**23. Why Vite?**

Fast dev server with HMR, fast production builds with Rollup/Rolldown. Zero-config for React via `@vitejs/plugin-react`. Native ESM.

**24. How does React communicate with Spring Boot?**

Through Axios. A configured instance (`axiosClient`) reads the JWT from localStorage and attaches it as a Bearer header on every request. The backend URL comes from a build-time environment variable (`VITE_API_BASE_URL`).

**25. How does React communicates with FastAPI?**

A separate Axios instance (`aiApi`) pointed at `VITE_AI_API_BASE_URL`. No JWT is attached — the AI service is public. Error handling is centralized via an interceptor that normalizes network and timeout errors.

## Deployment

**26. Why Docker?**

Reproducibility. The app is a mix of Node, Java, Python, and MySQL. Without containers, each environment differs. Docker makes the whole stack run the same way everywhere.

**27. What is Docker Compose?**

A tool for defining and running multi-container Docker applications from a single YAML file. It creates a shared network, manages volumes, and enforces service startup order via `depends_on` and healthchecks.

**28. Why use separate containers?**

Isolation, independent scaling, independent dependencies, and clean boundaries. Updating the AI model does not require rebuilding the backend. The frontend image can be swapped without touching the database.

**29. How do containers communicate?**

Over a shared Docker bridge network, addressed by service name. `backend` reaches MySQL at `mysql:3306` and the AI service at `ai-service:8000`. The browser is on the host network, so it uses published host ports.

## Testing

**30. How did you test the system?**

- Backend: `.\mvnw.cmd clean test` → 21 tests, 0 failures
- AI service: `pytest -v` → 86 passed, 2 xpassed
- Frontend: `npm run build` → 2606 modules, no errors
- Manual QA (Phase 13): 22 auth tests, 10 startup-flow tests, 9 investor-flow tests, 10 admin-flow tests, 14 error-state tests, 4 responsive breakpoints, 13 security tests

**31. What happens if the AI service is unavailable?**

Each AI page renders a red error card ("AI service is currently unavailable") with a Retry button. The failure mode was verified in Phase 13 by stopping the container and clicking the analyze buttons.

**32. How are unauthorized users handled?**

- Missing or invalid JWT → HTTP 401
- Wrong role → HTTP 403
- Cross-owner resource access → HTTP 404 (ownership checks return not-found, not forbidden, to avoid leaking resource existence)

## Limitations

**33. What are the limitations?**

- Synthetic dataset only
- Recommendation direction is investor → startups; reverse is future work
- Pitch analyzer is trained on templated text and underperforms on professional free-form prose
- 438 MB BERT model complicates GitHub upload
- No `/actuator/health` on the backend
- No real-world validation

**34. What would you improve in the future?**

- Real data and larger scale
- Reverse recommendation model
- Explainability with SHAP/LIME
- Real-time notifications and messaging
- Full CI/CD, monitoring, and MLOps
- HTTPS, cookie-based auth, rate limiting
